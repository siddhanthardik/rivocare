CRON Booking Fix Report

Summary:
- Problem: Cron and other processes crashed with error `Cast to ObjectId failed for value 'nurse'` when `Booking.service` was assigned a string (e.g., 'nurse', 'doctor', 'physio'). Booking.model enforces `service` as ObjectId, so writes of plain strings caused runtime errors.
- Root cause: Several API paths accepted `service` identifiers from clients as strings (slugs/names) and passed them directly to Mongoose methods expecting ObjectId. This produced cast errors and crashed some cron flows when those bookings were later read/updated.

Changes made:
- backend/src/controllers/bookingController.js
  - Now resolves incoming `service` values that are strings by looking up Service by `slug`, `name`, or `label` before using them as ObjectId.
  - If resolution fails, returns `400 Invalid service identifier` to the caller and logs a warning.
  - Uses the resolved ObjectId for provider checks and booking creation to avoid cast errors.

- backend/src/controllers/paymentController.js
  - When creating Booking from `payment.bookingIntent`, resolves `intent.service` similarly (slug/name → ObjectId).
  - If resolution fails, falls back to the first available Service in the database (best-effort) and logs a warning. If no Service exists, skips booking creation and logs an error, but continues processing payment to avoid blocking money flows.
  - This prevents creating Bookings with string `service` values.

Notes & rationale:
- Priority was to avoid schema violations and runtime crashes while preserving the existing payment and booking flows (no major behavior changes).
- For inbound API calls, returning `400` on invalid service identifiers prevents storing bad data and surfaces issues to callers.
- For `bookingIntent` created during payment flow, payments should not fail because of a missing service lookup; therefore payment processing continues while booking creation is skipped or uses a fallback service (best-effort) and warnings are logged for ops to investigate.
